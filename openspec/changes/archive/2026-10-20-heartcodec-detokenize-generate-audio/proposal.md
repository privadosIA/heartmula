# Proposal

## Why

C7 turned the codes of **one** 29.76 s segment into audio with parity against Python. A song is longer than that: `generate` produces up to minutes of frames, and heartlib's `detokenize` decodes them in overlapping windows, feeding the tail of each segment's latents back as in-context for the next one and cross-fading the audio. Without that loop the C# port cannot decode anything but the reference clip, and `generate` still stops at a `frames.safetensors` file nobody can listen to.

This change closes the pipeline: tokens of any length → audio, and `generate` → WAV.

What I measured reading heartlib (commit 5858ca8, `heartcodec/models/decoder.py`) and the C7 results (not repo code):

- `detokenize` works with `min_samples = int(29.76·12.5) = 372` code frames per window, `hop = 372 // 93 · 80 = 320` and overlap `372 − 320 = 52` code frames (104 latent frames). Short inputs are repeated until they reach 372 frames; longer ones are repeated and cut so that `(len − 52)` is a multiple of 320; the output is trimmed to `int(original_len / 12.5 · 48000)` samples. A 400-frame input therefore becomes 692 frames and 2 windows.
- Window 0 runs flow matching with no in-context. Each later window takes the last 104 latent frames of the previous window as in-context (`incontext_length = 104`), padded with fresh `torch.randn` to 744 frames, and runs `inference_codes` with `scenario = "other_seg"`. C7 implements that path (`FlowMatching.InferenceCodes` with `incontextLength > 0`, `otherSeg`) but only checked it with stub estimators: **no real data exercises it yet**.
- Each window's latents are decoded by the vocoder separately to 1 428 480 samples; consecutive windows are joined by a linear cross-fade over the last/first 199 680 samples (`ovlp = 1 428 480 − 1 228 800`).
- The existing fixtures hold one window only. A multi-window reference needs Python again (the golden venv was deleted at the end of C3; the recipe is in `tests/fixtures/MANIFEST.md` and takes about 5 minutes; the user allowed rebuilding it).
- `generate` today writes `frames.safetensors` and stops. HeartMuLa (7.3 GB in bf16) and the codec (6.3 GB fp32) do not fit together on the 12 GB RTX 4070; heartlib itself calls `_unload()` between the two stages. C7 measured 10.8 GiB of peak VRAM for flow matching + vocoder alone on that GPU, so the model must be gone before the codec loads.
- C7 found that cuDNN's default TF32 turns a 5.5e-3 error in the latents into a 36 dB audio; with TF32 off both GPUs equal the CPU at no measurable speed cost (10 steps took 3.6 s either way on the 4070).

## What Changes

- **Windowed decode** (`HeartCodecDecoder.Decode`): the window planning (repeat/pad/trim exactly as the reference), the in-context hand-over between windows, the per-window reorder + vocoder decode, the linear cross-fade and the final trim. Noise is injectable per window (the recorded fixture noise); by default it comes from the seeded `torch.randn` stream. `DecodeSegment` from C7 stays as the single-window case.
- **New multi-window fixture**, generated by extending `tools/dump_reference.py codec` with a long case: 400 reference-derived frames (2 windows), recording per window the codes, both noise tensors (the `randn` of `inference_codes` and the padding `randn` of the in-context hand-over), the latents, the vocoder input, and the final wav. About 12 MB of audio plus 6 MB of latents; `MANIFEST.md` documents the recipe (English). Python lives only in `tools/`; nothing from it runs at C# runtime.
- **Parity tests** against that fixture on CPU and both GPUs: per-window latents (this is the first real check of the in-context path), window-1 in-context frames, the cross-fade region and the full trimmed wav. Thresholds are measured first and then fixed with about 4× margin.
- **`generate` writes audio**: a `--wav <path>` option (PCM16 by default, `--wav-format float32` available) that, after the token loop, **unloads HeartMuLa**, loads the codec, decodes and writes the WAV. `frames.safetensors` is still written. The codec may run on a different device than the model (`--codec-device`), and cuDNN TF32 is turned off during the codec decode by default so GPU output equals the CPU's (`--codec-tf32` opts back in).
- **Unloading**: after the last frame the model's parameters and caches are disposed and the CUDA cache is released before the codec is read, so the 4070 never holds both.
- Reproducibility: with the same `--seed` and inputs, the WAV is the same on the same device (the codec noise follows the seeded stream after generation).
- README section (English) and an audio-for-listening test that decodes a real generated clip.

Out of scope: speed optimisation, bf16 codec, streaming playback, resampling or loudness handling, and any change to the HeartMuLa model or its sampling.

## Capabilities

### New Capabilities
- `codec-windowed-decode`: decoding codes of any length by overlapping windows with in-context latents and cross-fades, with parity against heartlib's `detokenize` (including the in-context path against real data).
- `audio-generation`: `generate` turns the generated tokens into a WAV file, unloading HeartMuLa before the codec, with reproducible output and the precision defaults that make GPU audio match the CPU.

### Modified Capabilities
None. (`codec-flow-matching` already specifies the in-context path of the solver; this change validates it with real data without changing its requirements.)

## Impact

- **Numerical parity criterion** (fp32): per-window latents and the full wav are compared with the thresholds of C7 as the starting bound (CPU `cos_sim ≥ 0.999999`, latents `max_abs ≤ 2e-5`, wav `max_abs ≤ 4e-6`), **measured first** and then fixed with about 4× margin; the in-context windows may need more room because window 1 depends on window 0's output. If the measured values do not meet the starting bound, the cause is investigated before relaxing anything.
- Code: `Codec/HeartCodecDecoder.cs` (windowing, cross-fade, long decode), `Pipeline`/`Program.cs` (`generate` stages, unloading, options) and new tests.
- Data: two new fixture files (≈ 18 MB) and a short-lived Python venv (deleted afterwards, recipe kept in `MANIFEST.md`).
- Hardware: CPU decode of 2 windows takes about 2 minutes; GPUs a few seconds. The full `generate --wav` with the real model is run on the GPU(s) with the machine otherwise idle.
- Audio: a real generated song is written to the Samba share and the user is asked to listen.
- Documentation: README, in English.
