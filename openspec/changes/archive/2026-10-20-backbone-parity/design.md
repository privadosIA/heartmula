# Design

## Context

- `check` (in `Program.cs`) compares `last_h` and `c0_logits` of the first frame by hand. With the real checkpoint on this machine it gives `cos_sim` 0,999987 and 0,999997, `max_abs` 0,0625 and 0,125 (bf16, CPU). It is the only comparison point that exists.
- The C1 fixtures (`tests/fixtures/`, see `MANIFEST.md`) already cover almost everything: `rope.safetensors`, `reference.safetensors` (prompt + first frame), `frames_py.safetensors` ([8,126] tokens generated with seed 1234) and `frames_logits.safetensors` (`c0_logits` [126,2,8197] and `last_h` [126,2,3072], raw, before CFG; call 0 is the prompt call, call t≥1 receives frame t−1).
- What they do **not** cover: the logits of codebooks 1–7 (decoder). With teacher forcing the decoder does not affect the backbone logits, so today there is no reference for it.
- `GenerateFrame` mixes backbone, sampling and decoder, and the sampling is random (not comparable with Python). `BackboneLogits` already separates the first half; the equivalent for the decoder is missing.
- The bf16 model on CPU takes 7,34 GiB and loading it takes ~16 s. The C2 `RealCheckpointFixture` class loads it once and measures the memory peak of the load; a second live model at the same time would inflate that measurement and double the RAM.

### torchtune vs HuggingFace differences that are respected (not touched; the tests verify them)

- torchtune RoPE: rotation by **adjacent pairs** `(x[2i], x[2i+1])`, not `rotate_half`; Llama 3 frequency scaling with `scale_factor=32`, `low=1`, `high=4`, original context 8192.
- RMSNorm computed in float32 and a parameter named `scale` (not `weight`).
- Boolean mask with `true = attend`, shape `[b, s, max_seq]`, indexing the causal one with `input_pos`.
- KV cache written by absolute position (`index_copy_`); torchtune uses an internal cursor. Equivalent as long as the positions are increasing and without gaps, which is the case with teacher forcing.
- Decoder without `tok_embeddings` or output layer (heartlib replaces them with `Identity`).

### Reference fixtures and how they were generated

- Existing: generated by `tools/dump_reference.py` (subcommands `prompt`, `rope`, `frames`) with heartlib at commit `5858ca8f…`, torch 2.10.0, torchtune 0.4.0, Apple M4 CPU, HeartMuLa in bf16, seed 1234, `cfg_scale` 1,5, `topk` 50. Details and sha256 in `MANIFEST.md`. They are not regenerated.
- New: `decoder_logits.safetensors`, generated on this machine by a `decoder` subcommand added to the same script (see decision 4).

## Goals / Non-Goals

**Goals:**
- Make parity with Python an automatic suite that fails by itself if someone breaks RoPE, attention, KV cache, embeddings, backbone or decoder.
- Cover all 126 frames with the cache growing, not only the first one, and both CFG rows separately.
- Be able to run the same tests on CPU and on CUDA, which is where the model will be used.
- Isolate each piece: a failure must point to RoPE, backbone or decoder, not "the model".

**Non-Goals:**
- Comparing sampling or frames generated by .NET with those of Python (random; that is C4 with other metrics).
- Tokenizer (C5) and codec (C6/C7).
- fp32 parity of the full model (there is no fp32 backbone fixture; see proposal).
- Optimizing performance or memory of the forward pass.

## Decisions

1. **A single shared model fixture.** `RealCheckpointFixture` becomes a collection fixture shared by the C2 tests and the parity tests, so that only one model is loaded and xUnit does not run the two classes in parallel. It loads on the device given by `HEARTMULA_DEVICE` (`cpu` by default). The peak memory test only applies on CPU and is skipped with an explicit reason on CUDA (the host RSS peak does not measure the same thing). The C2 tests that read `.bytes` of parameters go through `.cpu()`. Alternative: a second fixture for parity; rejected because it duplicates 7 GiB and falsifies the memory measurement.
2. **Teacher forcing in the backbone with the pieces that already exist.** Call 0: `reference.safetensors` (tokens, mask, pos, MuQ) as `check` does. Call t≥1: frame `t−1` of `frames_py` ([8]) is repeated in both rows, padded with the text column at `empty_id` and mask `false` in it, and the position is the last prompt position + t, exactly like the `MusicGenerationPipeline` loop. So as not to copy that logic into the test, the frame padding (`PadAudioToken`) goes from private to a reusable static function; the pipeline uses it just as before. Each call is compared with `frames_logits[t]` (row 0 = conditional, row 1 = unconditional) without applying CFG, which is how they were recorded. Alternative: call `GenerateFrame`; rejected because it samples and does not return the logits.
3. **Decoder with forced tokens without duplicating the loop.** The codebook loop of `GenerateFrame` is extracted into a private method that receives how to choose each token (sample, or read the one from Python), and `GenerateFrame` passes the sampler. A public method `DecoderLogits(lastH, tokens)` passes the forced one and returns the logits of codebooks 1–7 `[B, 7, V]`. This way the code under test is the same code that generates. To check that the extraction did not change the behavior, a test without checkpoint is added with a small model: `GenerateFrame` with `topk=1` (deterministic) matches the greedy chaining of `DecoderLogits`. Alternative: copy the loop into the test; rejected because it falls out of sync without anyone noticing.
4. **How the decoder fixture is generated.** `decoder` subcommand of `dump_reference.py` that runs the **real** heartlib `generate_frame` in teacher forcing: the module's sampling function is replaced with one that returns the tokens of `frames_py` and records the logits it receives, so the decoder logic is heartlib's and not a replica. It runs the 126 frames (it is the only way to have the backbone caches in real state), on CPU and bf16, and saves for 6 spread-out frames (0, 1, 2, 63, 124, 125; the decoder resets its cache on every frame, so they do not depend on one another) the `last_h` that the decoder received [n,2,3072], the tokens [n,8] and the logits [n,2,7,8197]. The `last_h` is saved in the fixture and the .NET test uses it as input, so it does not matter that it is not bit-for-bit the one from the Mac. Size ≈ 2,8 MB, versioned like the others. Alternative: a Python replica of the decoder loop (faster, but prone to differ from the original); rejected unless patching the sampling turns out to be impractical, in which case it is noted in the task.
5. **Tolerances.** `cos_sim ≥ 0.999` and `max_abs ≤ 0.5` on bf16 logits (≈4× what was measured on the first frame); `max_abs ≤ 1e-4` on F32 RoPE; 1 bf16 ulp on bf16 RoPE. The worst case per tensor and frame is always reported so the drift can be seen. If something fails the numbers are not relaxed: it is investigated and noted.
6. **Device.** `HEARTMULA_DEVICE=cpu|cuda` is read by the fixture; the fixture inputs are moved to the device and the results are brought back to CPU for comparison. On this machine it fits: 7,3 GiB of weights + ~1,9 GiB of KV cache on the 12 GB 4070.
7. **Python environment.** `~/.venvs/heartlib-golden` with torch 2.10.0 (CPU), torchtune 0.4.0 and heartlib at the pinned commit in `~/src/heartlib`, with the versions from `MANIFEST.md`. The system Python is 3.14, but there is `/usr/bin/python3.11`: the venv is created with that one.

## Risks / Trade-offs

- [The `max_abs` of some late frame exceeds 0,5 because of cache drift or accumulation order] → the cause is reported and the decision is made with data; the tolerance is not raised to make the test pass. The "no drift" test compares the last 26 calls with the first 26 to see it.
- [Parity uncovers a real failure in attention or decoder (it already happened with the RoPE cache)] → if the fix is small and in a single module, it is done here with its test; if not, work is paused and the scope is reconsidered.
- [Patching heartlib's sampling may not be possible without touching its code] → it is patched from the script without modifying heartlib; if that does not work, a replica of the loop, noting in tasks the difference from the original.
- [`torch==2.10.0` does not install with this machine's default Python (3.14)] → venv with `/usr/bin/python3.11`, the golden run version.
- [Setting up the venv downloads hundreds of MB and running 126 frames takes minutes on CPU] → it is a one-time cost; the resulting fixtures are versioned.
- [Refactoring the shared fixture may break the C2 tests] → they are run in full before and after, and the memory test keeps its measurement of the load.
- [The reference fixtures come from an Apple M4; this machine is x86 and CUDA accumulates in a different order] → this is what the bf16 tolerances absorb; it is measured on CPU and on CUDA.
