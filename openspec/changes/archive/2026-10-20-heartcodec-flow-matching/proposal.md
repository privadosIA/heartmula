# Proposal

## Why

HeartMuLa already generates music tokens (C4) from the right prompt (C5), reproducibly, and the codec's vocoder turns latents into audio (C6). The step in between is missing: HeartCodec's **flow matching** turns the 8 RVQ code streams into the latents the vocoder consumes. Without it nothing can go from tokens to a waveform, so `generate` cannot produce a song.

This change implements that half for **one segment**: RVQ code lookup, conditioning, the 30-layer DiT estimator, and the Euler solver with classifier-free guidance, plus the stereo reordering that feeds the vocoder. The reference fixtures cover exactly one segment (the 126 reference frames repeated to 372), so that is what can be validated now. The `detokenize` windowing loop for longer songs (overlapping segments, in-context latents, cross-fades) is a follow-up (C8) that needs a new Python-generated fixture.

What I measured reading heartlib (commit 5858ca8) and the HeartCodec-oss checkpoint (not repo code):

- `flow_matching` is 365 tensors, **5.97 GB of the 6.2 GB codec checkpoint**, all F32, about 1.5 B parameters. Inference needs 339 of them; the other 26 (`embed_avg`, `cluster_size`, `initted` for each of the 8 RVQ layers, and `project_in`) are EMA/training state.
- The estimator is a DiT with two stages (24 blocks of width 1536, 24 heads × 64; then 6 blocks of width 3072, 24 heads × 128), AdaLN-single time conditioning, RoPE on adjacent pairs, SwiGLU MLPs and kernel-3 `ProjectLayer`s. 326 tensors, which matches the architecture exactly (26 standalone plus 30 blocks × 10).
- Each Euler step runs the estimator on a batch of 2 (classifier-free guidance); 10 steps × batch 2 × 744 tokens × 1.5 B parameters is about 45 TFLOP: expect a minute or two on this 20-thread CPU and a few seconds on the GPUs.
- Fixtures that already exist (`codec_latents.safetensors`, `codec_wav.safetensors`, generated by `tools/dump_reference.py codec` on an Apple M4, fp32) hold the codes, the recorded noise that drives flow matching, the resulting latents, the reordered vocoder input and the final audio. That gives three checks: codes + noise → latents, latents → vocoder input (exact), and codes → audio end to end. There are no intermediate references (quantized features, per-step outputs), so each block is also tested against naive loops written in the tests.

## What Changes

- **Strict loader** for the `flow_matching.*` tensors, following the header-only validation pattern of `CodecWeights.LoadVocoder` and `HeartMuLaModel.LoadWeights`: one error listing every discrepancy before any data is read, tensor-by-tensor reads, and an **explicit allow-list** for the RVQ training-state tensors so they are ignored instead of reported as unexpected. `scalar_model.*` is not read here.
- **Flow-matching modules in C#/TorchSharp** with field names that replicate the checkpoint keys (no mapping table): RVQ code lookup plus `project_out`, `cond_feature_emb`, the ×2 nearest upsampling, the conditioning masks with `zero_cond_embedding1`, the DiT estimator (RMSNorm, adjacent-pair RoPE, attention with SDPA, SwiGLU MLP, `ProjectLayer`, AdaLN-single with the timestep embedding, LayerNorm without affine), and the Euler/CFG solver implementing the **full** `inference_codes`, including the in-context path (`incontext_length > 0`). Only `incontext_length = 0` can be checked against a fixture here, and that is stated clearly; the in-context path is validated against real data in C8.
- The noise is an **explicit parameter** so tests can inject the recorded noise; real use defaults to `torch.randn` on the seeded generator.
- A function that reorders `[B, T, 256]` latents into the `[2B, 128, T]` vocoder input, and a composed `codes → audio` decode of one segment.
- **Audio for listening**: with `HEARTMULA_AUDIO_DIR` set, a test writes `c7_codes_to_wav_csharp.wav` (codes → latents → vocoder, 483 840 samples) next to the Python reference, so the user can listen to the first audio produced **from tokens**.
- Time, peak memory and TF32 effects are measured on CPU and both GPUs and recorded.
- README section, in English.

Out of scope (follow-up C8): the `detokenize` loop for codes longer than 372 frames, a multi-segment fixture (needs Python), wiring `generate` to write a WAV, and unloading HeartMuLa before loading the codec on a 12 GB GPU.

## Capabilities

### New Capabilities
- `codec-flow-matching`: HeartCodec's flow matching in C# loads its weights strictly, turns RVQ codes into latents with parity against the Python reference, and decodes one segment to audio together with the vocoder.

### Modified Capabilities
None. (`codec-vocoder` does not change.)

## Impact

- **Numerical parity criterion** (fp32, latents are roughly unit-scale): `cos_sim ≥ 0.9999` as the starting bound, with `max_abs` and the signal-to-error ratio **measured first** on CPU and on each GPU and then fixed with about 4× margin. fp32 error accumulates over 30 layers × 10 Euler steps, so I do not guess the final numbers; if the measured values do not meet the starting bound, the cause is investigated before relaxing anything. The reordering and the code lookup are exact checks. End to end, the first 483 840 samples must match `wav` with the thresholds measured for the vocoder, adjusted by what is measured here.
- Code: new files under `src/HeartMuLa.Net/Codec/` (modules, solver, loader, reorder, composed decoder) and new tests.
- Data: no new fixtures, no Python.
- Memory: 5.97 GB of fp32 weights (the RTX 4070 has 12 GB, the RTX 5060 Ti 16 GB). They fit with the activations, but not next to the 7.3 GB HeartMuLa model, which matters for C8.
- Audio: produces audio; written to the shared Samba folder and the user is asked to listen.
- Documentation: README, in English.
